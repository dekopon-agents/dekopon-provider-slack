# Dekopon Slack provider

One Wasm component for separately granted Slack operations. The provider exposes `slack.canvas.lookup` (`slack canvas lookup TEXT`), returning `{canvasId,sections:[{id}]}` for **all** matching sections on the owner-pinned canvas. It makes one buffered `POST https://slack.com/api/canvases.sections.lookup` with `canvas_id` from `providerSettings.slack.canvasId` and `criteria.contains_text` from the typed input `{containsText}`. No channel or canvas ID is accepted from the caller. Zero matches fail `not-found`; empty queries fail `invalid-input` before HTTP. `ok:false` never succeeds.

`slack.canvas.read` (`slack canvas read`, no arguments) is a separately granted read-only capability with a closed empty input `{}`. It makes one buffered `POST /api/canvases.getContent` with `canvas_id` from the owner setting and `content_type: "markdown"`, and returns `{canvasId,markdown}` with the whole canvas as Slack renders it. Slack has no section-only read, so a caller reads, then edits one section through `slack canvas replace`, which still looks the section up fresh. Any argument, a section ID included, is a usage error. Non-200 responses and unrecognised `ok:false` fail `http-failed`; `canvas_not_found`/`canvas_deleted` fail `not-found`; `access_denied`, `missing_scope` and `canvas_disabled_user_team` fail `access-denied`; malformed JSON or a missing string `content` fails `invalid-response`; a host `response-too-large` fails `too-large`. Refusals echo no response body, Slack error text or setting value, and a read never writes partial content. Canvas text is untrusted data: the provider never parses it for instructions or IDs.

`slack.canvas.replace` (`slack canvas replace SECTION_MATCH MARKDOWN`) is a separate write capability that replaces one canvas block with one block. Slack's canvas sections are blocks: a heading, a paragraph and each list item are separate sections. `SECTION_MATCH` is text that must appear in exactly one block; it is search text, not a section ID, and the IDs `slack canvas lookup` prints are for information and are not replace input. `MARKDOWN` replaces only that block, so it carries only that block's new text, never the surrounding heading or neighbouring blocks. Block rule: after trimming, `MARKDOWN` must have exactly one non-empty line (`\n` and `\r` both end a line); two paragraphs, a heading with any other line, a list of two items, a table or a fenced code block fail `multiple-blocks` (exit 2) before HTTP, with a fixed message that echoes no input. Empty Markdown or an empty section match fail `invalid-input` before HTTP. The provider then freshly looks up `SECTION_MATCH`, requires exactly one ID (`not-found` or `ambiguous` otherwise), and sends one `POST /api/canvases.edit` with a single `replace` change naming that `section_id` and Markdown `document_content`. It makes exactly one verification lookup with the first 64 characters of the trimmed replacement line, and verification passes when the edited section ID is among the returned sections, whatever else also matches. Success returns `{canvasId,sectionId}`. Failures, with no retry and never a second edit:

| Code | When |
| --- | --- |
| `conflict` | Slack refused the edit as locked or stale (`canvas_editing_locked`, `canvas_locked`, `section_not_found`, `canvas_not_found`). |
| `unknown-result` | The edit's result is unknown: a transport failure after send, a non-200 or unparsable edit response, or an unrecognised `ok:false`. |
| `accepted-unverified` | Slack answered the edit `ok:true`, then the verification lookup failed or did not return the edited ID. The edit was accepted; read the canvas before any further edit. |

After any failure, run `slack canvas read` before another edit. Slack's `canvases.edit` and `canvases.sections.lookup` references document no guarantee that a section ID survives `replace`; if Slack assigns a new ID, the outcome is `accepted-unverified`, never success. This is best effort, not atomic or a lost-update guarantee. Offline synthetic untouched-section comparisons are not proof of live preservation or ID stability.

`slack.post` (`slack post CHANNEL TEXT [THREAD_TS]`) independently proposes typed `{channel,text,threadTs?}` and sends one `POST /api/chat.postMessage` with `channel`, `text` and optional `thread_ts`. Successful Slack `ok:true` returns `{channel,ts}`. Invalid thread timestamps refuse before HTTP; Slack refusals and uncertain post outcomes do not retry. For edit and post sends, pre-send HTTP refusals fail `http-failed`; uncertain HTTP outcomes fail `unknown-result`, without retry. A failed verification lookup after an accepted edit always fails `accepted-unverified`. A post grant is not a thread fence: a subject-specific broker forbid is needed for a fenced post.

| Owner-only `providerSettings.slack` | Behaviour |
| --- | --- |
| `canvasId` | Required for canvas calls; absent, null, empty or wrong type fails `invalid-settings` before HTTP. |
| `baseUrl` | Optional for all calls; defaults to `https://slack.com`. HTTPS DNS host and optional port only, no path. Invalid values fail `invalid-settings` before HTTP. Omit in production; the component fixture uses `https://slack.com:<ephemeral-port>`. |

Settings are resolved at the authorized call, not broker boot; neither key is model-facing. Post does not require `canvasId` or any canvas scope. The guest never sends an authorization header; the broker injects a separately destination-bound credential. No token, scopes, grants or live workspace access are provided by this repository. An offline fixture does not establish Slack bot entitlement or live content preservation.

For the eventual deployment, use the DekoponVille bot token through a broker copy; **the gateway copy also gains canvas-write reach** when those scopes are approved. Lookup and read use `canvases:read` and replace uses `canvases:write`; no file or channel scopes. `slack.post` uses the existing `chat:write` scope and is independently granted, with no implicit thread fence. Canvas operations require a deployed broker pre-DNS fixed-ID body forbid (method, host, path, no query, `canvas_id`), not merely this setting; the manifest must pin both IDs together. Read needs its own `request-fences.cedar` forbid on `slack.canvas.read` (POST, `slack.com`, `/api/canvases.getContent`, no query, the pinned `canvas_id`, `content_type == "markdown"`); it is a Cedar forbid, not a request template, because core refuses non-GET templates. Do not deploy canvas permits before their forbid. Deployment HTTP ceilings follow `gh.yaml`: `slack.com` POST, 10 s, one request, 16,384 request bytes and 262,144 decoded response bytes; replace overrides three requests and 15 s; read inherits the family's one request, 10 s and 262,144 decoded response bytes, with no lower guest cap. A canvas over that ceiling surfaces as a broker host rejection (`byte-limit`), so no content reaches the caller. No standalone or whole-canvas edit is authorized. Releases, credential copies, bindings, grants and deployment are separate owner actions.

Build and test with the commands in [AGENTS.md](AGENTS.md). The SDK and testkit are both pinned to `=0.46.1`; the component is `slack-provider.wasm`. Tests use synthetic decoded JSON section IDs, synthetic canvas text and a synthetic canvas ID, not recorded Slack traffic or proof of the broker forbid. The native read → lookup → replace → read cycle over a synthetic block-per-section canvas, with a repeated heading and the replacement text also present in another block, proves what the provider sends, not Slack's live preservation of untouched sections.
